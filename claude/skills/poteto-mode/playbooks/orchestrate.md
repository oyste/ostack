### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, check what each one produces, and let a human approve every merge.** For a standing project handed to one coordinator chat: multi-day, many PRs, dozens of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program. Plan the program first with the Multi-phase plan playbook, which names this playbook as its executor.

Run it with your own tools. Spawn workers with `Agent`, `subagent_type: "poteto-agent"`. In T3 Code, use `delegate_task` for a worker on another provider's model or in its own checkout. Keep the program's state in the plan file and a `notes.md` beside it, outside the repo. Watch each PR with the harness's PR watcher when it has one, such as T3 Code's `watch_pull_request`. Otherwise the owner's **babysit-pr** skill watches it. Run no polling loops of your own, and never relay messages or status between agents.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge-ready, then merges it with the **full-send** skill. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Give every worker that writes code its own git worktree (`isolation: "worktree"`), named after its branch. Pick each subagent's reasoning level for the job, per the Subagents section.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Resume when new work needs a worker's built state,** such as its checkout, uncommitted changes, or a running process. Message a worker only for a follow-up on the same work. Never message one to check on it, because a message restarts an idle agent.
- **Each PR gets a verifier that isn't its author,** on a different model family where the harness offers one, such as the **sol-loop** or **council** skill. The owner merges only after that verifier's pass at the current head, a human approval, and green required checks. The **full-send** merge gate enforces the last two. Never merge with `--admin` or any other bypass.
- **Start with one unit.** Take it through kickoff, owner, verifier, approval, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a check through the project's verification skill (`verify-*`), or an artifact. It also names the goal, the base branch, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks`, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Batch the human's work.** Approving PRs is the human's job, not a blocker to fix. Collect every PR that waits only on approval into one message with each PR's link, what it changes, and its verdict, and keep other work moving meanwhile.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, the PRs waiting on approval, what was dropped and why, and the decisions waiting on the user.
